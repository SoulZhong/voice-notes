# E3 spike:CATap + 私有聚合设备(路线 A)实测报告

> issue #99 二期的 E3。判据在 `docs/2026-08-12-clock-drift-sensor-design.md` 第五节,
> 预注册,本文只填数字不改判据。工具:`src-tauri/examples/catap_spike.rs`。
>
> **本文只是探针结论,路线 A 尚未裁决通过,采集主干一行未动**——把未验证的采集路径
> 合进主干,风险大于收益(issue #99 留言已立此规矩)。

## 一句话现状

路线 A 在本机(macOS 26.5.2)**技术上完全跑得通**:私有聚合设备 + 全局 CATap,
单 IOProc 同时出 mic 与系统输出两轨——**每次回调两轨帧数都相等**(43143 次回调零例外,含一场 370s 全程)、
**跨域场内容级错位曲线 6 分钟无台阶**(设备级时间戳断层也是 0,但那只是旁证,见判据 2 一节);开销:IOProc 回调占用 0.05~0.07% 单核、本进程采集期 CPU
0.17~0.19% 单核,**coreaudiod 侧的 tap/聚合/重采样开销未测**(那才是路线 A 的主要成本项)。

**drift 补偿确实在工作**:同时钟域(内置麦 + 内置扬声器)的对照场读出精确的
+0.00ppm(采集轨 = 参考 ×0.0499 的纯增益,缩放后残差 0.49%);跨时钟域(内置麦 +
蓝牙输出)读出 -3.26ppm,
量级与"蓝牙域 − 内置域"的独立旁证相符(差 0.15ppm)。**但这不是残余的定量上界**
——那 0.15ppm 的吻合依赖"蓝牙栈按主机重定时"这个未在本机直接测量的前提。

**裁决不能下**,缺五块:判据 1 的**声学口径**(要 mic 真听见播放内容,且播放侧得在
**另一个时钟域**——同域场测了不说明补偿好坏)、播放侧时钟误差的独立测量、判据 3 热插拔
完全未测、判据 4 只测了终端身份没测签名 app、判据 2 还欠一场"跨域 + 严阈值"的长跑。另外走 A 就要为 13.x–14.1 维护双栈采集路径,这笔成本要与 B
(DLL 闭环 + rubato 变比重采样)的实现成本一起算。

## 工具

```bash
cd src-tauri
cargo run --example catap_spike -- list      # 列输入设备 + uid
cargo run --example catap_spike -- probe     # 能力/授权探针:只建拆设备,不落音频
cargo run --example catap_spike -- capture --secs 370 \
    --input-uid BuiltInMicrophoneDevice --out /tmp/catap
cargo run --example catap_spike -- capture --secs 370 --native --out /tmp/catap  # 原始率落盘
```

`capture` 默认落两条 16k mono s16 轨(`mic.wav` / `system.wav`),与 app 的规范轨同格式,
`bin/xcorr_align` 可直接读。

`--native` 按设备原始率(48k)落盘。**与外部参考文件比对时必须加这个**:探针里的
48k→16k 是无抗混叠的线性抽取,宽带内容(白噪)一混叠,波形相关性就没了——第一次参考
对照实测 corr 只剩 0.10,就是栽在这上面。轨间(mic vs system)比对不受影响,因为两轨
走同一条抽取、误差同相抵消。

### 踩坑:selector 名猜错 = 进程 abort

第一版按直觉发 `setPrivateTap:`,结果 ObjC 抛 unrecognized selector,而 **Rust 接不住
外来异常,整个进程直接 abort**(`fatal runtime error: Rust cannot catch foreign exceptions`)。
CATapDescription 没有公开头文件可查版本差异,所以探针改成先问运行时要方法表再发:

```
UUID  bundleIDs  deviceUID  init  initExcludingProcesses:andDeviceUID:withStream:
initMonoGlobalTapButExcludeProcesses:  initMonoMixdownOfProcesses:  initMonoMixdownOfProcessesIDs:
initStereoGlobalTapButExcludeProcesses:  initStereoMixdownOfProcesses:  initStereoMixdownOfProcessesIDs:
initWithDictionary:  initWithProcesses:andDeviceUID:withStream:  isExclusive  isMixdown  isMono
isMuted  isPrivate  isProcessRestoreEnabled  name  processes  setBundleIDs:  setDeviceUID:
setExclusive:  setIsExclusive:  setMixdown:  setMono:  setMuteBehavior:  setName:  setPrivate:
setProcessRestoreEnabled:  setProcesses:  setStream:  setUUID:  stream
```

两个与直觉不符的事实:**私有属性的 setter 是 `setPrivate:`(不是 `setPrivateTap:`)**;
**没有 `initExcludingProcesses:` 的短形式**,只有带 `andDeviceUID:withStream:` 的长形式。
所以产品化时凡是发可选 selector,一律先 `respondsToSelector:`。

## capture 实测(370s,内置麦为 master + 蓝牙耳机为输出)

设备组合是刻意选的:master 是内置麦(48k),被 tap 的输出走蓝牙耳机——**两个独立硬件
时钟域**,是路线 A 最难的场景。若换成内置麦 + 内置扬声器,两者同一时钟域,测了也不说明问题。

三条读表的注意事项:

- **逐回调对账是后加的**(Codex 审查指出:只比最终累计长度撑不住"每次回调都等长"这个
  说法——某次少给、下次补回来,累计照样相等)。两场 370s 跑在加仪表之前,只有累计数;
  补测的 60s/30s 两场逐回调核过,8449 次回调**一次不等都没有**。
- **"聚合设备时钟 vs Instant"这一行只是粗筛,任何一栏都别当 ppm 级证据**:首/末回调
  的时刻各带一个缓冲块(512 帧 ≈ 10.7ms)的粒度误差,370s 上仍有 **±29ppm** 的分辨率下限
  (30s 上更是几百 ppm)。所以 -3.7 / -2.1 / -14.3 这些读数彼此的差别没有意义,它们
  **不能**给下面的 -3.26ppm 做旁证(Codex 十九轮指出;初稿把 -3.7 当成可用值是错的)。
  这一行的唯一用处是抓**量级错误**——比如第一场那个 -154.6ppm 的口径 bug,它就是这么
  暴露出来的。要真的量聚合设备时钟,得用设备时间戳做回归,那是另一件事。
- 最后一栏 **system rms 恰为 0**:那次没放任何音频。这反过来证明前几场 system 轨里的
  信号确实来自 tap 抓到的播放内容,不是底噪或串扰。
- **断层判据的容差后来收紧过**:最初按"跳变 > 1 帧"算断层,那会漏掉系统只补/丢**整一帧**
  的硬校正——恰恰是判据 2 要抓的东西(Codex 十二轮指出)。现在按 > 0.5 帧算。
  表里前两场 370s 是旧阈值下测的,故按新阈值补跑了第三场 370s:34694 个回调全部带有效
  时间戳、断层仍为 0,逐回调帧数与 buffer 参差也都是 0。

**"回调占用"不等于 CPU 成本**(Codex 审查指出):它只是本进程 IOProc 内部的墙钟耗时,
既不含 coreaudiod 里 tap / 聚合设备 / drift 重采样的开销,又混进了回调被抢占的时间。
探针已改为同时打印 `getrusage`,并且取的是**采集期增量**(起流前后各一次快照)——
第一版把快照放在落盘之后,把写两条几分钟长 WAV 的开销算了进去,0.06% 报成了 0.67%;
只取一次绝对值也不行,进程启动那几百毫秒会把短跑的数字抬高好几倍。
即便如此,**系统侧开销仍未测**——真要给路线 A 的 CPU 成本下结论,得另外量 coreaudiod。

第一场的"实测源域率"打成了 -154.6ppm,是探针自己的口径 bug:分母用了
`AudioDeviceStart → 停止` 的整段墙钟,两头各混进一截与采样无关的时间(设备启动延迟
~0.2s、主循环 200ms 轮询粒度)。改成"首回调 → 末回调"之后读数就落回 -3.7ppm,
与传感器口径吻合。**教训:任何"实测速率"都要先说清分母是哪两点之间。**

"两轨帧数相等"不是巧合,是路线 A 的**结构性保证**:单 IOProc 一次回调同时给出两轨,
帧数天然相同(补测里 8449 次回调逐次核对,零例外)。这正是它相对现状(mic 走 cpal、
system 走 SCK,两条独立时钟各自交付)的根本优势。

### 一个反面观察:蓝牙耳机做 master 时 mic 会中途哑掉

15s 冒烟那次用 Shokz(HFP 16k)当 master,前 6 秒 mic 有声、之后掉到 0.0003 的静音底噪,
而 system 轨全程正常。原因是播放触发了 A2DP/HFP 的 profile 切换。这与路线 A 无关
(现状架构同样会遇到),但说明**蓝牙组合的 E2 数据要单独看**,不能与内置麦混在一个分布里。

## 残余漂移:参考对照到底量到了什么

判据 1 说的是**轨间残余错位**:同一个真实声音,在 mic 轨与 system 轨里的样本位置之差
随时间怎么变。mic 就是 master 时钟本身,所以这一项 = tap 经 drift 补偿后相对 master
时间轴的残余速率误差。直接量法是**声学口径**:让 mic 真听见播放内容,
`xcorr_align system.wav mic.wav` 取斜率。

本次做的是**参考对照**:把播放用的参考文件与 system 轨互相关。先把它到底测什么推清楚
(第一版在这里想错过,靠下面的对照实验才纠回来):

- 播放端按标称比例把文件渲染进输出设备的时钟域(一秒内容 → 48000 个输出域样本);
- tap 抓到的就是这条流,drift 补偿把它重采样到 master 域:一秒真实时间里输出设备产出
  `R_o` 个样本,补偿要交付 `R_m` 个,于是内容被缩放 `R_m/R_o`;
- 落盘按标称 48000 除三。分析脚本量的是"采集索引 − 参考索引",补偿每个输出域样本交付
  `R_m/R_o` 个 master 域样本,故**读数 ≈ (R_m − R_o)/48000**(Codex 十三轮纠正了这里的
  方向:是 master 减播放侧,不是反过来),即两个时钟域**之差**。
  注意这句话的准确含义(Codex 十四轮再纠):抵消的是**两域共有**的那部分误差,不是
  "master 的绝对误差自动消失"——若播放侧恰好准(R_o≈48000),读数就等于 master 自己的
  误差。所以要从读数里分离补偿残余,**两个时钟域各自的误差都得有独立测量**。

关键推论:**补偿没生效时读数反而是 0**(不重采样 = 样本数原样传递),读数非零恰恰说明
补偿在按两域之差做重采样。

### 对照实验(同时钟域):0.00ppm,波形吻合到 0.49% 残差

补跑的第三场 370s 恰好赶上耳机断开、输出回到**内置扬声器**——播放与采集同属一个硬件
时钟域。读数:

```
粗对齐 corr 1.000 / 窗数 37 / 斜率 +0.00ppm / 拟合残差 rms 0.000ms
```

**"corr 1.000" 不等于逐样本一致**(Codex 十三轮指出,初稿就是这么写错的:增益缩放或直流
偏移一样能给出 Pearson 1.0)。逐样本核过之后的准确说法是:在精确滞后处采集轨 =
参考 × **0.0499** 的纯增益(那就是播放时的 `afplay -v 0.05`),**缩放后残差仅占 0.49%**
(量化 + 16k→48k→16k 往返的代价),错位全程不变。

这条对照排除了"整条量测链(播放→tap→抽取→互相关)自己带漂移或根本不灵敏"的可能:
同域时它读出精确的 0,跨域时才读出非零。

核对时的一个副产品:滞后**差 2 个样本**就足以把 Pearson 从 1.0 压到 0.72(参考噪声的
有效带宽比设计时以为的宽)。这正好解释了跨域那场大量窗只有 0.1~0.2 的相关——
抽取相位随漂移滑移,并不代表峰位置不对。

### 跨时钟域:-3.26ppm

第二场 370s(内置麦 master + **蓝牙耳机**输出,两个独立晶振):

```
窗数 31 / 斜率 -3.26ppm = -11.7ms/小时 / 拟合残差 rms 0.019ms max|resid| 0.037ms
整段错位变化: 首窗 +0.062ms → 末窗 -1.062ms (跨度 360s)
```

按上面的模型,这 3.26ppm 就是**补偿实际施加的缩放**,量级应等于蓝牙域与内置域之差。
旁证:本机传感器测得内置麦相对主机时钟 -3.11ppm(E2 的 8/15 那场),而蓝牙栈按 host
重定时(E2 里蓝牙 HFP 麦实测 ≈0ppm,与业界做法一致)——若蓝牙域≈主机域,两域之差就该
≈3.1ppm,与实测的 3.26ppm 差 0.15ppm。

**能得出什么**:补偿确实在跨域时做重采样,量级与独立旁证相符;错位曲线 6 分钟内最大
偏离直线 0.037ms、无台阶——这是**内容级**的"无跳变"证据,判据 2 主要靠它。

**不能得出什么**:补偿残余的定量上界。上面那 0.15ppm 的吻合依赖"蓝牙域 ≈ 主机域"这个
未经本机直接测量的前提;真要给残余定数,要么独立量播放侧时钟,要么走声学口径
——后者按构造只剩残余本身,是判据 1 的正解。

### 复现命令(分析脚本已入库)

```bash
python3 scripts/drift_vs_ref.py <参考.wav> <采集目录>/system.wav
```

**为什么不是 `bin/xcorr_align`**:它只收 corr>0.5 的窗,而跨域那场大量窗落在 0.1~0.2,
按它跑只剩 6 个点(斜率 -3.36ppm,与全窗结果差 0.1ppm)。低相关窗的**峰位置仍然正确**
——错位读数一个不落地排在同一条斜坡上,被压低的只是峰值,原因是探针那个无抗混叠的
48k→16k 抽取相位随漂移滑移。要根治就加 `--native` 按原始率落盘(轨间比对不受影响,
那条路两轨走同一条抽取)。

低相关窗能用、又不能什么都收,靠的是**峰显著性**而非相关值本身:脚本用中位数+MAD 估
背景涨落,只收高出背景 6 个稳健标准差、且邻域外没有可比次峰的峰。这条门槛是必需的
——Codex 实测过,两条毫不相干的噪声轨搜几千个滞后也能凑出 0.02~0.03 的"峰",据此能
拟合出 +2052ppm 的漂亮假结果。脚本另外挡掉的假通过(都拿实测/构造数据验过):全静音轨、
恒定直流的"数字静音"、周期性 click 串(多滞后并列)、参考轨短于一个窗。

## 判据逐条对照(预注册,`clock-drift-sensor-design.md` 第五节)

| # | 判据 | 状态 |
| --- | --- | --- |
| 1 | 残余轨间漂移中位 <20ppm 且 1h 错位 <10ms | **未收口**:参考对照 -3.26ppm 与"补偿生效"一致,但分离不出残余(播放侧时钟未独立测);判据口径(声学)待做 |
| 2 | 错位曲线无跳变(无系统内部硬校正) | **部分**:跨域场的**内容级**错位曲线 6 分钟无台阶(最大偏离直线 0.037ms);设备级时间戳断层 0 次,但见下方两条限制 |
| 3 | 设备热插拔不崩、行为可解释 | **未测** |
| 4 | TCC 授权体验可接受 | **部分**:从终端跑无提示、无拒绝,tap 直接建成并拿到真实系统音频;签名 .app 内的表现未测 |

判据 1 为什么说"未收口":本次量的是参考对照口径,里面同时混着 master 时钟误差与
**播放侧时钟误差**,而后者一路都没独立量过,所以任何减法都分离不出补偿残余,更给不出
数值区间(见上节)。判据原文说的轨间错位要用**声学口径**(mic 真听见播放内容)直接量
——那条口径里共模项按构造抵消,读数就是残余本身。预注册的判据不能拿"按推理应该没问题"
顶替实测。

判据 2 的两条限制(Codex 十三轮):
1. 探针数的是**聚合设备输入时间戳**的连续性,它描述的是 master 设备的交付节奏,
   **看不见 tap 内部**的补偿动作——补偿器完全可以在帧数不变、输入时间戳连续的情况下
   丢/补/重采样 tap 内容。所以"断层 0 次"是设备级旁证,不能单独支撑判据 2;
   真正的证据是内容级的错位曲线线性度(跨域那场已有)。
2. 严阈值(>0.5 帧)的时间戳检查只在**同域**那场 370s 跑过;两场跨域用的是旧的 >1 帧
   阈值,理论上会漏掉整一帧的校正。**跨域 + 严阈值 + 全覆盖**的那一场还欠着。

判据 4 需要补充说明:本次是从终端(继承终端的 TCC 身份)跑的,**没有弹任何授权框**,
tap 与聚合设备都建成了、也真的拿到了系统音频内容。这不等于 app 内也一样——
产品化要在签名 bundle 里复测,并确认 Info.plist 需要哪些用途声明。

## 还差什么才能裁决

1. **声学口径的判据 1**:内置麦 + 一个**自带时钟**的外放、安静房间、≥10 分钟,播 E1
   标定序列,`xcorr_align system.wav mic.wav` 取斜率。10 分钟能分辨到 ~2ppm
   (1 样本 = 62.5µs)。
   **外放设备的选法是这条实验的成败关键**(Codex 十七轮):要的是**另一个时钟域**,
   合格的只有 **USB 声卡/USB 音箱**(自带晶振)或**蓝牙设备**;
   **不合格**:内置扬声器,以及插在 3.5mm 耳机/线路输出上的**模拟有线音箱**
   ——后者换的只是换能器,时钟仍是内置输出 DAC 那一颗,做出来等于重跑同域对照,
   残余天然为 0(第三场已实测 +0.00ppm),会让判据 1 假通过。
2. **判据 2 收口:跨域 + 严阈值 + 全覆盖的一场长跑**。已有的严阈值(>0.5 帧)长跑只在
   同域场做过,两场跨域用的是旧的 >1 帧阈值。用当前版本的探针在**跨时钟域**下再跑一场
   ≥370s,确认「断层 0 次 + 时间戳覆盖 100%」;上面第 1 条若按跨域外放来做,这一条顺带
   就完成了(同一场采集,看探针输出的断层与覆盖两行即可)。
   注意这仍只是设备级旁证,内容级证据要看那一场的错位曲线线性度。
3. **热插拔(判据 3)**:采集中途拔/换 mic 设备、切默认输出设备,观察 IOProc 是否继续、
   聚合设备是否失效、进程是否崩,以及断层计数。
4. **签名 app 内的 TCC(判据 4)**:同一套代码放进 bundle 跑一遍。
5. **13.x–14.1 双栈成本**:app 最低 macOS 13.0,CATap 要 14.2+。走 A 就得同时维护
   新旧两条采集路径,这笔账要与 B(DLL 闭环 + rubato 变比重采样)的实现成本一起算。
