# 声纹向量的模型空间正确性 设计

日期：2026-08-19
状态：待实施（范围经五轮 Codex 设计 review 后收窄，见「为什么是这个范围」）
配套：`2026-08-19-voiceprint-write-consolidation-design.md`（推迟的收口重构，保留全部分析）

## 要解决的问题

用户切换声纹模型（CAM++ ↔ ERes2NetV2）之后，库里的向量与新模型不在同一个向量空间。代码有一道门禁（不同空间不可比，宁可不认也不乱认），但**没有任何一层知道"这组向量属于哪个模型空间"**，于是：

- 切模型重建成功、库标签已是新的；此时一个更早启动、用旧模型算完的写入落盘，库里就混进了旧空间的向量。库标签仍是新的，**启动自愈也检测不出来**——它只比标签，不比内容
- `restore_merged_person` / `undo_merge` / `restore_feedback` 把**存档里的整份质心原样插回**。而 `rebuild_for_model` 结尾会 `invalidate_all` 把全部合并日志标记失效，`restore_merged_person` **恰恰只接受已失效的日志**——重建之后任何一条老日志都能被「拆回」，把旧空间质心插进新库
- 写库时声明的模型标签只靠调用方自觉传对；缓存槽存的是无身份的 `Box<dyn SpeakerEmbedder>`，trait 本身没有标签

## 三条不变量

三者**互不依赖、可独立实施与测试**，都不涉及锁、队列、录制路径。

### 一、新算的向量写入必须声明模型空间

写向量的方法增加 `model: &str` 参数（调用方声明"我这组向量是用哪个模型算的"）。方法内部取锁之后、动数据之前比对库当前 `embedding_model`；不等则丢弃、返回 mismatch、记日志与遥测（新增 `ErrorKind::VoiceprintSpaceMismatch`）。

**覆盖**：`upsert_from_session`、`reinforce_feedback`、`merge_with_embedder` / `merge_journaled`。

**不覆盖 `append_sample` / `append_sample_for_merge`**：它们写的是原始录音 WAV，与模型无关，而且正是重建赖以重算质心的素材。按旧标签拒绝只会丢掉有价值的原声。

**丢弃而不是报错**：声纹是增值功能，绝不能因它异常挡住主流程（既有哲学，见 `load_voiceprint_seeds` 注释）。但**必须留痕**——2026-08-19 的教训正是"系统连续 149 次知道自己坏了却什么都不做"。

**mismatch 必须清理占位账**：`reinforce_feedback` 因 mismatch 返回时，此前写下的 `complete=false` 占位条目必须删除，否则该 scope 会被永久判为"已回灌过"、此后永不重试。测试须同时断言库与 ledger 都不变。

`rebuild_for_model` 仍是唯一能改 `embedding_model` 的写入。

### 二、历史快照回放必须带模型标签

新增两个持久化字段（均 `#[serde(default)]`）：`MergeJournalEntry.embedding_model`、`LedgerEntry.embedding_model`。

**标签来源**：journal 标签在写快照时取自**当时库的 `embedding_model`**（`MergePrior` 走 `merge_journaled(..., None, ...)`，没有嵌入器可问）；ledger 标签取自通过模型比对并成功提交的那次写入。

| 快照标签 | 处置 |
|---|---|
| 等于库当前标签 | 照常整份还原 |
| 不等于，或旧条目缺该字段 | 只还原身份元数据（名字、redirects、样本文件副本），**`centroids` 与 `session_centroids` 两张表都清空** |

**两张表都要清**：种子注入与自动归并同时消费这两张表，只清主质心仍会把旧空间的会话质心注入新模型。测试须断言两张表皆空，且 `seed_clusters` 不再为该人产出种子。

**选"清空"而不是"拒绝回放"**：人被拆回来了、名字在、样本文件也还原了，只是暂时没有声纹——下次重建就从样本重新长出来。拒绝回放会让用户彻底拿不回这个人。

**`restore_feedback` 的执行顺序**（避免实现者绕过 CAS）：

1. 先做原有 CAS：库当前状态必须等于账本记的 `after`；不等则不动，返回 `touched-since`
2. CAS 通过后：同模型 → 恢复完整 `before`；异模型 → 恢复去掉两类质心的 `before`

**样本恢复是硬条件**，`restore_merged_person` 与 `undo_merge` 都算：两者现在都是"先恢复人物 → best-effort 复制样本 → 删 journal"。清空质心之后**样本是唯一可跨模型恢复的依据**，一次复制失败就是永久丢失。改为：样本恢复失败 → **保留 journal 不删**；「人物已存在」的重试分支要**继续补样本**再收尾，补样本必须幂等、只补缺失、不覆盖既有。

**清空质心之后必须排一次重建**，否则那个人永远长不回来（库标签已是当前模型，启动自愈不会再动它；`append_sample` 只写 WAV 不产生质心）。做法：store 层回放方法返回 `needs_rebuild: bool`，调用方**在释放 VP 锁之后**调 `spawn_voiceprint_rebuild`。

**不是直接置 `REBUILD_PENDING`**：那不是队列，只有已有重建在跑时置位才有意义，空闲时置位不会启动任何东西。适用于**所有异模型回放**，不只"样本刚恢复"那一种。

### 三、模型标签与声纹计算器绑死

`model` 参数若只靠调用方自觉传对等于没有保证：现有缓存槽存的是无身份的 `Box<dyn SpeakerEmbedder>`，trait 本身也没有标签，重建线程"核对设置 → stash 实例"与 `set_settings` 清缓存之间仍有窗口。

改为 `TaggedEmbedder { model: String, inner: Box<dyn SpeakerEmbedder> }`：标签在**构造实例时绑定**，无法脱离。缓存槽与会话载体都存它；取用时若 `model` ≠ 当前选型则丢弃重建。写库时的 `model` 一律取自该结构，调用方无从传错。

## 配套：取消关联不做连带撤销

「取消关联」只清 `speakers.json` 的 `person_id`，表项与段落归属都不动，显示回落到「新说话人 N」。

**不撤销这次关联带来的声纹回灌。** 代价：库里那个人多留一段本不该有的样本。

理由：连带撤销要求"撤销任务"与"回灌任务"两个后台任务正确排序，而它们只隔着一把不保证顺序的门。前三轮代码 review 里最难缠的几条 P1（反向执行竞态、`MergePrior` 漏复核、账本误撤）根源全在这里。**砍掉撤销任务，这些问题不是被堵住，是不存在。**

保留 `spawn_feedback` 提交前的关联复核（用户可能改派给另一个人，或 identify 自动应用改了关联）——它便宜且正确。

## 数据与兼容

- 新增两个持久化字段，均 `#[serde(default)]`
- 旧条目无该字段 → 视为来源不明，按不变量二只还原身份、清空两张质心表
- `voiceprints.json` 的 `embedding_model` 语义不变
- 无破坏性迁移，无新增锁文件

## 测试

- **旧模型写入被拒**：库标签 B，以 A 调 `upsert_from_session` / `reinforce_feedback` / `merge_journaled`，断言库**与 ledger**都不变且返回 mismatch
- **原始录音不受门禁**：以任意标签调 `append_sample`，断言正常写入
- **快照回放**：库标签 B，回放标着 A（或无标签）的合并日志与回灌账，断言身份回来了、两张质心表皆空、`seed_clusters` 不再产出该人
- **`restore_feedback` 顺序**：CAS 失败时库一字不变；CAS 通过且异模型时恢复的 `before` 不含两类质心
- **样本恢复是硬条件**：`restore_merged_person` 与 `undo_merge` 各一条——失败时 journal 必须保留；重试只补缺失、不覆盖既有
- **异模型回放触发重建**：返回 `needs_rebuild=true`，调用方在释放锁后发起
- **`TaggedEmbedder`**：标签≠当前选型的实例不得被取用
- 现有 1393 条 Rust 测试不得变红

## 为什么是这个范围

原计划是把声纹库的写入整体收口（见配套文档）。经五轮 Codex 设计 review 后收窄，理由：

**没有收敛。** 五轮的 P1 数是 2 → 5 → 6 → 4 → 8。第五轮（按"单一写入者队列"结构性重写之后）比第四轮还多。

**队列消解的比预期少。** Codex 第五轮的映射表：前四轮 17 条 P1 里，队列真正消解的只有 4 条（锁嵌套自死锁、两类重活占门、identify 不可重入）；其余多数是模型一致性、崩溃事务、因果撤销、调度存活性问题，**只是换了位置**。

**当前队列设计按字面实施跑不起来。** 录制期的实时入库在 ASR worker 里**同步**调用、当场要 `person_id` 才能继续，而录制 writer **整场持着该笔记的锁**——"执行者每项先拿笔记锁"会让这个请求整场重排，调用方永远等不到。修好它要先决定录制期入库的语义，那会改变录制行为。

**范围已经越出"声纹库"。** Codex 列出的"必须同步等结果"的调用点包括实时入库、停录快照、identify 应用与撤销、人物合并/拆回/确认、改名、删除——那是整条说话人身份链路，不是一个子系统。

本文这三条不变量是那份分析里**可以独立成立、且不触碰锁与录制路径**的部分。它们合起来消灭"旧模型的向量写进新库"这一整类问题——也正是 2026-08-19 那台机器出问题的那一类。

**跨进程一并推迟**：`notelock.rs` 的注释明确把"来自另一个应用实例"当作真实场景并记录过数据事故，而代码里没有任何单实例约束。已核实 MCP stdio 子进程只 `load()` 声纹库、只读关联不写，但那只是暴露面的一半。要么加单实例约束、要么给声纹库加跨进程锁——两者都归入推迟项。
