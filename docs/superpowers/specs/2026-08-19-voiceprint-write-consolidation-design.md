# 声纹库写入收口 设计

日期：2026-08-19
状态：待实施（Codex review 四轮共 17×P1 + 9×P2 已并入；第五版按「单一写入者队列」重写，见文末「修订记录」）
起因：2026-08-19「取消关联」功能三轮 codex review，每轮都在新位置发现同类问题

## 背景与根因

用户报告「逐字稿换说话人无效、说话人无法取消关联」。前者是显示层 bug（NodeView 缓存了徽章 DOM），已修，与本设计无关。后者是缺功能，实现过程中 codex review 三轮共 10 条 P1，**每轮修完下一轮都在不同位置冒出同类问题**——按 systematic-debugging 的判据，这是架构问题。

根因：**声纹库的写入没有归属权。** 互不相识的任务在改同一个 `voiceprints.json`——录制结束的 session 回写、指认触发的回灌与人物合并、取消关联触发的撤销、换模型触发的重建、identify 的自动应用与自动撤销。它们之间只隔着 `VP_LOCK`（决定谁先写文件）与 `FEEDBACK_GATE`（只锁其中一部分）。于是：

- **没有任何一层知道"这组向量属于哪个模型空间"**——切模型重建之后，一个更早启动、用旧模型算完的写入落盘，库里混进旧空间向量，而库标签仍是新的，启动自愈也查不出来（它只比标签不比内容）
- **复核与写入不原子**——后台任务确认"该说话人仍关联着目标人物"再写库，中间会被改关联的路径插入。`MergePrior`（把一整个人物并进目标）不由取消关联回滚，一旦发生就留在库里
- **历史快照回放绕过一切检查**——`restore_merged_person` / `undo_merge` / `restore_feedback` 把存档里的整份质心原样插回，而 `rebuild_for_model` 结尾会把全部合并日志标记失效、`restore_merged_person` 恰恰只接受已失效的日志

## 关键决定：单一写入者队列

前四版设计试图用锁与门的组合去约束这些任务，每一轮 review 都在补一个新的协调机制：单飞标志、排队标志、门、退避、变更回执、locked 变体。**这些都是队列自带的东西。**

第五版改为：**声纹库与说话人关联的所有变更，由一个执行者线程串行执行。** 其余代码只往队列里提交请求。

这不是"再加一层机制"，而是**用一个机制替掉四个**。下列前四版的产物随之删除：

- `FEEDBACK_GATE` 的协议扩张（用户点击排队、非阻塞试锁、退避重排）
- transition receipt 穿过 actor 传递
- identify 的 `*_locked` 变体（不可重入问题随单线程消失）
- `REBUILD_RUNNING` / `REBUILD_PENDING`（重建只是队列里的一项，重复请求去重即可）

### 队列的形状

**请求**（示意，非最终签名）：

```
enum VpRequest {
    AssignPerson  { note, speaker, person },     // 用户点「选人」
    ClearPerson   { note, speaker },             // 用户点「取消关联」
    RenamePerson  { person, name },              // 用户改名
    IdentityApply { note, op },                  // identify 自动应用
    IdentityUndo  { note, op },                  // identify 自动撤销 / 崩溃恢复
    Reinforce     { note, prepared },            // 回灌(载荷已在提交前算好)
    Rebuild,                                     // 换模型重建 / 启动自愈
}
```

**优先级**：用户点击 > identify 自动路径 > 回灌 / 重建。

用户点「选人」时若后台正在给别的笔记回灌，用户那条插到队首——**这是前四版做不到的**：那些方案只能让用户排在后台重活后面等。

**执行者每处理一项**：

1. 取该笔记的 `NoteLock`（与录制 writer、转码、重转写、Aing 提交互斥——它们都持这把锁）
2. 校验**准备数据的版本指纹**（见下）
3. 校验**模型空间标签**（见不变量一）
4. 写关联 / 写声纹库
5. 释放

**`NoteLock` 拿不到就重排，不原地等**：`acquire()` 只试约 100ms，而录制 writer 整场持锁、转码与重转写是分钟级。执行者拿不到就把该项**延迟重新入队并继续处理下一项**——不阻塞后面的高优先级请求（否则一篇正在录的笔记会造成队头阻塞）。

**重活不进队列。** 解码、嵌入、模型加载必须在**提交之前**做完，结果随请求带进来；否则一个几分钟的任务会把队列堵死。

### 版本指纹仍然必需

队列保证"执行时不被插入"，但**不保证提交时的依据到执行时还成立**——重转写会在这中间把整篇段落换掉。所以提交的载荷要带指纹，执行时比对：

- 原始稿：speaker + 排序后的 `(seq, source, start_ms, end_ms)` 指纹
- 修订稿：revision + speaker + source_seqs 指纹
- 音频轨道元数据签名

对不上就丢弃或重排，**绝不拿旧段算出的嵌入去写当前 scope**。

准备阶段还要**短持一次 `NoteLock` 取稳定的音频快照**再放开：转码持锁时会 rename M4A、删 WAV，不持锁读会在 `exists` 与 `read` 之间踩空。

## 仍然需要的不变量

### 一、向量写入必须声明模型空间

写向量时声明"这组向量是哪个模型算的"，执行者在写库前比对库当前标签；不等则丢弃、返回 mismatch、记日志与遥测（新增 `ErrorKind::VoiceprintSpaceMismatch`）。

**覆盖**：`upsert_from_session`、`reinforce_feedback`、`merge_with_embedder` / `merge_journaled`。
**不覆盖 `append_sample` / `append_sample_for_merge`**：它们写的是原始录音 WAV，与模型无关，正是重建赖以重算质心的素材。

**丢弃而不是报错**：声纹是增值功能，绝不能因它异常挡住主流程。但**必须留痕**——2026-08-19 的教训正是"系统连续 149 次知道自己坏了却什么都不做"。

**mismatch 必须清理占位账**：`reinforce_feedback` 因 mismatch 返回时，此前写下的 `complete=false` 占位条目必须删除，否则该 scope 会被永久判为"已回灌过"、此后永不重试。

`rebuild_for_model` 是唯一能改 `embedding_model` 的写入。

### 二、历史快照回放必须带模型标签

新增两个持久化字段（均 `#[serde(default)]`）：`MergeJournalEntry.embedding_model`、`LedgerEntry.embedding_model`。

**标签来源**：journal 标签取自被快照那一刻库的 `embedding_model`（`MergePrior` 没有 `TaggedEmbedder` 可用）；ledger 标签取自通过模型比对并成功提交的那次写入。

| 快照标签 | 处置 |
|---|---|
| 等于库当前标签 | 照常整份还原 |
| 不等于，或旧条目缺该字段 | 只还原身份元数据（名字、redirects、样本文件副本），**`centroids` 与 `session_centroids` 两张表都清空** |

**两张表都要清**：种子注入与自动归并同时消费这两张表，只清主质心仍会把旧空间的会话质心注入新模型。

**`restore_feedback` 的执行顺序**：先做原有 CAS（库当前状态必须等于账本记的 `after`，不等则不动、返回 `touched-since`）；CAS 通过后，同模型恢复完整 `before`，异模型恢复去掉两类质心的 `before`。

**样本恢复是硬条件**，`restore_merged_person` 与 `undo_merge` 都算：清空质心之后样本是唯一可跨模型恢复的依据，一次复制失败就是永久丢失。样本恢复失败 → 保留 journal 不删；「人物已存在」的重试分支要继续补样本再收尾，且补样本必须幂等、只补缺失、不覆盖既有。

**清空质心之后必须排一次重建**（否则那个人永远长不回来：库标签已是当前模型，启动自愈不会再动它，`append_sample` 只写 WAV 不产生质心）。做法：store 层回放方法返回 `needs_rebuild`，执行者据此往队列里追加一项 `Rebuild`。适用于**所有异模型回放**。

### 三、模型标签与声纹计算器绑死

`model` 参数若只靠调用方自觉传对等于没有保证：现有缓存槽存的是无身份的 `Box<dyn SpeakerEmbedder>`，trait 本身也没有标签。

改为 `TaggedEmbedder { model: String, inner: Box<dyn SpeakerEmbedder> }`：标签在**构造实例时绑定**，无法脱离。缓存槽与会话载体都存它；取用时若 `model` ≠ 当前选型则丢弃重建。写库时的 `model` 一律取自该结构。

## 明确不做

- **不做跨进程锁。** 已核实：MCP stdio 子进程只 `load()` 声纹库、只读关联（`mcp/tools.rs` 的 `person_id` 引用全是读出来报给调用方），不写；voice-notes 是客户端程序，不会起第二个写入进程。前四版的「不变量五」整条删除
- **队列不持久化。** 崩溃/强退时未执行的请求丢失，表现为"这次指认没学进声纹库"。可接受：声纹回灌是增值功能，下次指认还能再学；而持久化要处理"执行到一半崩了"的半完成状态，正是这个子系统已经栽过跟头的地方（存档回放那条 P1 就是"部分成功之后怎么办"没定义清楚）
- **非向量写入不做模型标签校验**（改名、邮箱、删人没有"模型空间"这回事）。但它们**要走队列**——声纹库每次变更都是整份 `load → save`，改名同样能用旧快照把刚完成的重建整体盖回去
- 不检测"库里已经混进了异空间向量"这一历史污染。本设计只保证此后不再发生；已有污染需一次重建清掉

## 数据与兼容

- 新增两个持久化字段：`MergeJournalEntry.embedding_model`、`LedgerEntry.embedding_model`，均 `#[serde(default)]`
- 旧条目无该字段 → 视为来源不明，按不变量二只还原身份、清空两张质心表
- `voiceprints.json` 的 `embedding_model` 语义不变
- 无破坏性迁移，无新增锁文件

## 测试

- **串行性**：并发提交多种请求，断言执行顺序与优先级一致、且任意时刻只有一个在写
- **优先级**：后台回灌排队时提交用户请求，断言用户请求先执行
- **`NoteLock` 拿不到不丢任务**：模拟长期持锁者，断言该项被重排且后续高优先级项照常执行（不发生队头阻塞）
- **版本指纹**：提交后段落被重转写替换，执行时必须判不一致并丢弃
- **旧模型写入被拒**：库标签 B，以 A 提交回灌，断言库**与 ledger**都不变
- **原始录音不受门禁**：以任意标签调 `append_sample`，断言正常写入
- **快照回放**：库标签 B，回放标着 A（或无标签）的合并日志与回灌账，断言身份回来了、两张质心表皆空、`seed_clusters` 不再产出该人
- **`restore_feedback` 顺序**：CAS 失败时库一字不变；CAS 通过且异模型时恢复的 `before` 不含两类质心
- **样本恢复是硬条件**：`restore_merged_person` 与 `undo_merge` 各一条，失败时 journal 必须保留、重试只补缺失
- **异模型回放触发重建**：返回 `needs_rebuild` 且队列里确实追加了 `Rebuild`
- **`TaggedEmbedder`**：标签≠当前选型的实例不得被取用
- **临时文件不互删**：并发两路解码同一笔记同一信道，两边都拿到完整 PCM
- 现有 1393 条 Rust 测试不得变红

## 修订记录

**Codex 设计轮一**（2×P1 + 2×P2）：快照回放漏网 → 新增两个持久化字段；「写方法内部持 `vp_guard`」+「后台任务先持 `vp_guard` 再调它们」会自死锁 → 改用 `FEEDBACK_GATE`；`model` 来源未固化；`append_sample*` 移出门禁范围。

**Codex 设计轮二**（5×P1 + 3×P2）：actor 等门会阻塞整个录制控制面，`identify_note` 在门内做分钟级重活；修订稿关联路径与 identify 自动路径未纳入协议；`VP_LOCK` 只有进程内原子性；样本恢复失败仍删 journal；质心置空须清两张表；清空后无重新长出的触发点；`restore_feedback` 的 CAS 与回放顺序自相矛盾。

**Codex 设计轮三**（6×P1 + 2×P2）：枚举"所有改关联的路径"这条路本身走不通（又漏了 Aing 提交、重转写提交、活动 writer）→ 改为借用笔记的 `NoteLock`；`REBUILD_PENDING` 不是队列；`undo_merge` 也要纳入样本硬条件；普通回灌的重活同样在门内；`track_pcm` 固定临时名会互删；`MergePrior` 的 journal 标签来源与 mismatch 占位账。

**Codex 设计轮四**（4×P1 + 2×P2）：「关联写入者一律不动」撤回（`prior` 写入后不可恢复）→ 需要 transition receipt；门外算的嵌入未与锁内真值绑定 → 版本指纹；`NoteLock` 只试 100ms 且不可重入，长期持锁者众多 → 需要退避协议；identify 路径需 locked 变体；`recover_identify_ops` 未纳入协议。

**第五版重写（用户提出，2026-08-19）**：用**单一写入者队列 + 优先级**替掉前四版累积的协调机制。

- 前四版一直在零散重新发明队列的部件（单飞、排队标志、门、退避、回执、locked 变体）。第一版把"引入队列"写成非目标，四轮 review 的证据说明那个判断是错的
- 队列直接消解设计轮四的三条 P1：拿不到锁不再需要退避协议（重排即可）、不可重入问题随单线程消失、transition receipt 不再需要（改关联与后续处理是同一个执行者按序做的）
- 优先级带来前四版做不到的能力：用户点击插队，不必排在后台重活之后
- 跨进程不变量整条删除——已核实 MCP 子进程只读、且本程序不会起第二个写入进程
- 队列不持久化：崩溃丢失未执行的请求，代价是"这次没学到"，好过引入半完成状态
