# 声纹库写入收口 设计

日期：2026-08-19
状态：待实施（Codex review 两轮共 7×P1 + 5×P2 已并入，见文末「修订记录」）
起因：2026-08-19「取消关联」功能三轮 codex review，每轮都在新位置发现同类问题

## 背景

用户报告「逐字稿换说话人无效、说话人无法取消关联」。结论分两半：

- 「换说话人无效」是显示层 bug（段落徽章是 ProseMirror NodeView 里的命令式 DOM，显示名不在节点 attrs 里，节点 `eq` 时 PM 复用旧 NodeView，即便整份重建也不刷新）。已修，与本设计无关。
- 「取消关联」是缺功能。实现它的过程中，codex review 三轮共 10 条 P1，**每轮修完，下一轮都在不同位置冒出同类问题**：

| 轮次 | P1 | 位置 |
|---|---|---|
| 一 | 3 | 重建的快照与单飞、撤销凭据、反向执行竞态 |
| 二 | 3 | 重建代次的提交点、`MergePrior` 漏复核、账本键 |
| 三 | 4 | 重建无界循环、旧模型在途写入、复核不原子、旧键删错 |

按 systematic-debugging 的判据，**三轮以上、每轮换个地方冒出来 = 架构问题**。停止打补丁，改为收口。

## 根因

声纹库的写入**没有归属权**。互不相识的任务在改同一个 `voiceprints.json`：录制结束的 session 回写、指认触发的回灌与人物合并、取消关联触发的撤销、换模型触发的重建、identify 的自动应用与自动撤销。

它们之间只隔着 `VP_LOCK`（进程内，决定谁先写文件）与 `FEEDBACK_GATE`（只锁其中一部分）。三条缺口：

**一、没有任何一层知道"这组向量属于哪个模型空间"。**
切模型后重建成功、库标签已是新的；此时一个更早启动、用旧模型算完的写入落盘，库里就混进了旧空间的向量。库标签仍是新的，**启动自愈也检测不出来**——它只比标签，不比内容。

**二、复核与写入不原子。**
后台回灌在 `FEEDBACK_GATE` 内读笔记确认「该说话人仍关联着目标人物」再写库，但**改关联的路径不取这把门**。`Reinforce` 尚可由随后的撤销补救，`MergePrior`（把一整个人物并进目标）**不由取消关联回滚**，一旦发生就留在库里。

**三、历史快照回放绕过一切检查。**
`restore_merged_person` / `undo_merge` / `restore_feedback` 把**存档里的整份质心原样插回**。而 `rebuild_for_model` 结尾会 `invalidate_all` 把全部合并日志标记失效，`restore_merged_person` **恰恰只接受已失效的日志**——重建之后任何一条老日志都能被「拆回」，把旧空间质心插进新库。

## 目标与非目标

**目标**

- 旧模型空间的向量永远写不进新库（从根上，不靠调用方自觉）
- 「检查关联 → 写库」不可被任何关联变更插入
- 换模型重建期间，其它写入进不来
- 上述保证在多进程下同样成立

**非目标**

- 不引入 actor / 消息队列做库写入。更大的机制，解决同一问题，不必要
- 不做乐观版本号（每次写带库版本、冲突重试）
- 不收非向量写入（改名、邮箱、删人、合并关系的账目操作）。它们没有"模型空间"这回事

## 设计

六条不变量。

### 一、新算的向量写入必须声明模型空间

写向量的方法增加 `model: &str` 参数（调用方声明"我这组向量是用哪个模型算的"）。方法内部取锁之后、动数据之前比对；不等则丢弃、返回 mismatch、记日志与遥测（新增 `ErrorKind::VoiceprintSpaceMismatch`）。

**覆盖**：`upsert_from_session`、`reinforce_feedback`、`merge_with_embedder` / `merge_journaled`。

**不覆盖 `append_sample` / `append_sample_for_merge`**：它们写的是原始录音 WAV，与模型无关，而且正是重建赖以重算质心的素材。按旧标签拒绝只会丢掉有价值的原声。

**丢弃而不是报错**：声纹是增值功能，绝不能因它异常挡住主流程（既有哲学，见 `load_voiceprint_seeds` 注释）。但**必须留痕**——2026-08-19 的教训正是"系统连续 149 次知道自己坏了却什么都不做"。

`rebuild_for_model` 是唯一能改 `embedding_model` 的写入，整段持锁。

### 二、历史快照回放必须带模型标签

新增两个持久化字段（均 `#[serde(default)]`）：`MergeJournalEntry.embedding_model`、`LedgerEntry.embedding_model`。

回放时比对：

| 快照标签 | 处置 |
|---|---|
| 等于库当前标签 | 照常整份还原 |
| 不等于，或旧条目缺该字段 | 只还原身份元数据（名字、redirects、样本文件副本），**`centroids` 与 `session_centroids` 两张表都清空** |

**两张表都要清**：种子注入与自动归并同时消费这两张表，只清主质心仍会把旧空间的会话质心注入新模型。测试须断言两张表皆空，且 `seed_clusters` 不再为该人产出种子。

**`restore_feedback` 的执行顺序必须明确**（避免实现者绕过 CAS）：

1. 先做原有 CAS：库当前状态必须等于账本记的 `after`；不等则不动，返回 `touched-since`
2. CAS 通过后：同模型 → 恢复完整 `before`；异模型 → 恢复去掉两类质心的 `before`

**样本恢复是拆回的硬条件**：`restore_merged_person` 现在的样本复制失败只记日志、随后照样删 journal。清空质心之后**样本是唯一可跨模型恢复的依据**，这一失败就是永久丢失。改为：样本恢复失败 → 保留 journal 不删；「人物已存在」的重试分支要继续补样本再收尾。

**清空后要有重新长出来的触发点**：回放发生时库标签已经是当前模型，启动自愈因标签一致不会再重建，`append_sample` 只写 WAV 也不产生质心——"暂时没有声纹"会无限期持续，下一场还可能新建重复人物。因此样本恢复成功后**排一次当前模型的重建**（走既有 `REBUILD_PENDING` 通道）。

### 三、关联变更去排后台任务那条队——但门不能由 actor 去等

所有**改关联**的路径在动手之前取 `FEEDBACK_GATE`：

- 原始稿：`assign_note_speaker_person`、`clear_note_speaker_person`
- 修订稿：`do_assign_refined_person`
- identify 的自动应用与自动撤销

**门必须由命令线程持有，不能由 lifecycle actor 去等。** actor 是单线程串行信箱，开录、停录、实时段落写入、改标题、删段全从它过；让它阻塞在门上，等于「给旧笔记选人的同时，另一篇正在录的笔记整个卡住」。做法：命令在 `spawn_blocking` 里先取门，再 `request(EditNote{...})` 并等回执，拿到回执后才放门。actor 本身不碰门。

**每个后台任务必须在门内复核自己那份文档的当前关联**（原始稿查 `speakers.json`，修订稿查修订稿的说话人表）。"修订稿没有取消入口"不能代替复核——同一簇可以再次改派给另一个人物。

### 三之二、identify 的重活必须移出门

`identify_note` 目前在 `FEEDBACK_GATE` 内解码整场音轨并逐段重嵌入，长会议是**分钟级**。不变量三把用户点击也放进这条队之后，这会直接表现为「点选人卡几分钟」。

改为：解码与嵌入在取门之前完成，门内只做读-改-写。这是不变量三能够成立的前提，不是可选优化。

**纪律要求（写进注释）**：`FEEDBACK_GATE` 的持有面已从"后台任务之间"扩大到"用户点击也排这条队"。此后任何往门内添加长耗时操作的改动，都会直接表现为点按钮卡顿。

### 四、模型标签与声纹计算器绑死

不变量一的 `model` 参数若只靠调用方自觉传对，等于没有保证：现有缓存槽存的是无身份的 `Box<dyn SpeakerEmbedder>`，trait 本身也没有标签，重建线程"核对设置 → stash 实例"与 `set_settings` 清缓存之间仍有窗口。

改为 `TaggedEmbedder { model: String, inner: Box<dyn SpeakerEmbedder> }`：标签在**构造实例时绑定**，无法脱离。缓存槽与会话载体都存它；取用时若 `model` ≠ 当前选型则丢弃重建。写库时的 `model` 参数一律取自该结构，调用方无从传错。

### 五、声纹库需要跨进程锁

`VP_LOCK` 是模块静态 `Mutex`，只在进程内有效。而本仓库明确支持多实例（并已为笔记引入跨进程 `NoteLock`）。两个进程可各持自己的 `VP_LOCK`：旧进程读标签 A 通过检查，新进程重建并写 B，旧进程随后用 A 的快照覆盖文件——既混入旧向量，又把库整体盖回旧标签。

抄 `store::notelock` 的现成模式，为声纹库加一把跨进程文件锁，覆盖 `load → 模型比对 → save` 全段，以及 journal 与样本迁移。

**当前实际暴露面**：已核实 MCP 子进程只 `load()` 声纹库、不写（`mcp/tools.rs:551/565`），所以眼下能撞上的只有"开两个 GUI 实例"，macOS 由 LaunchServices 天然拦着，Windows 可能。**是真漏洞但眼下打不到**——仍要修，因为不变量一的承诺是"永远写不进"，留个进程边界的洞就不成立。

### 六、重建的触发保持一次性 + 排队

沿用已实现的 `REBUILD_RUNNING` 单飞 + `REBUILD_PENDING` 排队，**不因"库标签仍不一致"自动重跑**（永久失败时会变成无界循环）。真正的模型切换必经 `set_settings`，那条路会置 `PENDING`；其余"卡住"情形由下次启动的自愈兜，一次启动最多一轮，天然有界。

## 数据与兼容

- 新增两个持久化字段：`MergeJournalEntry.embedding_model`、`LedgerEntry.embedding_model`，均 `#[serde(default)]`
- 旧条目无该字段 → 视为来源不明，按不变量二只还原身份、清空两张质心表
- `voiceprints.json` 的 `embedding_model` 语义不变
- 新增声纹库跨进程锁文件（位置与命名比照 `NoteLock`）
- 无破坏性迁移

## 测试

- **旧模型写入被拒**：库标签 B，以 A 调 `upsert_from_session` / `reinforce_feedback` / `merge_journaled`，断言库不变且返回 mismatch
- **原始录音不受门禁**：以任意标签调 `append_sample`，断言正常写入
- **快照回放**：库标签 B，回放标着 A（或无标签）的合并日志与回灌账，断言身份回来了、`centroids` 与 `session_centroids` 皆空、`seed_clusters` 不再产出该人
- **`restore_feedback` 顺序**：CAS 失败时库一字不变；CAS 通过且异模型时恢复的 `before` 不含两类质心
- **样本恢复是硬条件**：样本复制失败时 journal 必须保留；重试路径补齐样本后才收尾
- **清空后有触发点**：样本恢复成功后 `REBUILD_PENDING` 被置上
- **关联取消后回灌不落库**；**`MergePrior` 同样受复核保护**
- **修订稿路径同样受保护**：修订稿改派后旧任务不得写入旧人物
- **`TaggedEmbedder`**：标签≠当前选型的实例不得被取用；写库参数取自该结构
- **actor 不阻塞**：命令持门期间，actor 仍能处理其它消息（以信箱可见性构造）
- 现有 1393 条 Rust 测试不得变红

## 已知不做

- 非向量写入不收口（见非目标）
- 不检测"库里已经混进了异空间向量"这一历史污染。本设计只保证此后不再发生；已有污染需一次重建清掉，而重建本就是用户可触发的动作

## 修订记录

**Codex review 设计轮一**（2×P1 + 2×P2）：快照回放漏网 → 新增两个持久化字段；原方案"写方法内部持 `vp_guard`" + "后台任务先持 `vp_guard` 再调它们"会自死锁（`std::sync::Mutex` 不可重入）→ 改用 `FEEDBACK_GATE`；`model` 来源未固化 → 新增不变量四；`append_sample*` 移出门禁范围。

**Codex review 设计轮二**（5×P1 + 3×P2）：

- actor 等门会阻塞整个录制控制面，且 `identify_note` 在门内做分钟级重活 → 门改由命令线程持有（不变量三），并把 identify 的重活移出门（不变量三之二）
- 修订稿关联路径与 identify 自动应用/撤销未纳入协议 → 不变量三覆盖全部关联写入路径
- 不变量四只是纪律、数据结构保证不了 → `TaggedEmbedder`
- `VP_LOCK` 只有进程内原子性 → 新增不变量五（跨进程锁）
- 拆回时样本恢复失败仍删 journal，而新方案里样本是唯一恢复依据 → 样本恢复改为硬条件
- 质心置空须同时清 `centroids` 与 `session_centroids`
- 清空后无自动重新长出的触发点 → 样本恢复成功后排一次重建
- `restore_feedback` 的 CAS 与回放顺序在文档内自相矛盾 → 明确为先 CAS 后回放
