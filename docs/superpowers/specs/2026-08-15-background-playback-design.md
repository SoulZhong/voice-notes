# 切页继续播放 + 全局迷你播放条

> 本文是第二版。初版经 Codex 审查判出 9 个 P1,核实后全部属实——初版把"验证了三条
> 前提"误当成"方案成立",实际缺一个完整的所有权与身份状态机。修订记录见文末。

## 问题

播放笔记音频时切到其他页面(设置/会议搭子/图谱等),播放会中断。

播放引擎本身在 Rust 里(单条 cpal 输出流按 offset 混音,WebView 只画 UI),切页本不该
断——断的原因是 `AudioPlayer.svelte` 的装载 `$effect` 清理函数调了 `player_stop`。

## 目标行为

| 场景 | 行为 |
| --- | --- |
| 播放中切到**非笔记页** | 继续播,右下角出现圆形浮层播放器 |
| 播放中打开**另一篇笔记** | 停下当前,新笔记页干净的未播放状态 |
| 在笔记页上 | 浮层隐藏(完整播放器已在页面里) |
| 左键点浮层 | 播放 / 暂停 |
| 右键点浮层 → 回到笔记 | 跳回那篇笔记页,**并从原位置续播** |
| 右键点浮层 → 关闭播放 | 停止播放,浮层消失 |
| **只是看过笔记、从未播放** | **不出现浮层** |
| **开始录制** | 停止播放并关闭浮层 |
| **删除正在播放的笔记** | 先停播放再删 |

**形态(2026-08-15 改版)**:右下角**圆形浮层**,直径约 56px。圆环周长表示播放进度,
圆心是播放/暂停按钮(左键);次要操作收进**右键菜单**:「回到笔记」「关闭播放」。

为什么从底部通栏改成角落圆形:通栏条横跨整个窗口宽度,遮挡面积大;而当时那套
"用 `bind:clientHeight` 测量条高、回填 `.main` 的 `padding-bottom`"的避让在真机上**没有
生效**(用户截图证实内容仍被压住)。角落小圆占用面积极小、不与正文争版面。

**一处需要更正的判断**:改版当时我把失效原因归为"设置页内部有 `height:100%` /
`overflow:hidden` 容器,父级 padding 对它们无效"——事后核实**这个说法不成立**,设置页的
根容器只是普通的 `padding: 1.5rem` 流式布局,理应吃得到父级 padding。真实原因更可能是
那条 `bind:clientHeight` → `$bindable` 的高度回传链没有生效,`miniPlayerHeight` 始终为 0。
形态改版的结论不受影响(角落圆形本就更合适),但原因不该以讹传讹。

~~**仍然存在的限制**:`graph/+page.svelte` 这类**内部自管理滚动**的页面(`height:100%` +
自己的 `overflow-y:auto`),父级安全区确实帮不上忙——浮层仍可能盖住其右下角内容。~~

**这条限制经实测不成立(2026-08-15 更正,第二次同类误判)**。用无头 Chromium 复刻
`shell → main.with-orb-safearea → graph-main(height:100%) → entity-stage → edge-inspector`
整条真实类链后量得:视口 800px 高时,graph 页内容底边在 **696px**,浮层顶边 **712px**,
两者不相交;`.main` 的内容盒被 `padding-bottom: 104px` 压掉后,`height: 100%` 的子树
按内容盒解析,整页跟着抬到了浮层上方。也就是说**百分比高度恰恰是会跟着安全区走的**,
"自管理滚动"并不构成例外(反例应是 `position: fixed` 或按 `100vh` 定高的元素——全库
除 `.shell` 自身外没有这种底部元素)。

同一份口径连错两次(先归因设置页容器、再归因 graph 自管理滚动),根子都是**没量就下
结论**。护栏落在 `src/lib/orbSafeArea.test.ts`:守住"尺寸/离边距只有一份 token、安全区
按同一组 token 算、两边同源判定"这三条前提——几何本身单测量不了,但前提一破,几何必错。

进度环**只读不可拖拽**:要精确跳转就右键回笔记页,那里有波形和逐句时间戳。

## 核验过的既有事实

1. `player_load` 在发布锁内递增代次并 `stop_stream`(`player.rs:639`)——打开笔记 B
   **后端**会停下 A。
2. 音轨是 `TrackBytes::Mmap`(`player.rs:34`)——无全量堆复制,驻留页可被 OS 回收。
   (初版写"几乎不增加 RSS"不准确:顺序播放会 fault 页面,那些页仍计入 RSS。)
3. `onPlayerPos` 订阅目前挂在 `AudioPlayer.svelte:134` 内,组件一卸载就没了。

**以下三条是初版误判,必须写进设计:**

4. 新 `Core` 创建时写死 `cursor=0, playing=false`(`player.rs:767`)——回到笔记页
   **位置不会自动续上**,必须显式 seek。
5. 装载 `$effect` 依赖 `tracks`,**转码完成重拉、续录、A/B 切换都会重跑它的 cleanup**
   ——cleanup 不等于组件卸载。
6. `player_pos` 事件不带任何身份(`events.ts:115`)——停 A→装 B 的窗口里,排队中的
   A 事件会写进 B 的状态。

## 会话(session)≠ 已装载内核

初版最大的设计错误:用一个 `noteId` 同时表示"后端已装载"和"用户有活动播放"。
播放器**进页就自动装载**,于是只是看过一篇笔记、从没点播放,离开后也会冒出浮层。

**会话由用户真正开始播放才建立**,不是装载建立:

```
session: { gen: number, noteId: string, title: string, totalMs: number } | null
currentMs, playing        // 由带 gen 的位置事件驱动
```

- **建立**:`player_play` 成功时
- **结束**:✕ / 装载了另一篇笔记 / 开始录制 / 删除该笔记 / 显式 `player_stop`
- 播放自然结束**不**结束会话(保留 `playing=false`,可重播)

## 身份与竞态:事件必须带代次(后端要改)

初版声称"后端零改动",错。`player_pos` 不带身份,store 无法判断事件属于哪次装载。

**最小后端改动**:`player_pos` 事件负载增加 `gen`(装载代次)。代次本就是后端概念、
`player_load` 已经返回它,不必新增 note_id 之类的业务字段。

store 只接受 `gen === session.gen` 的事件,其余丢弃。这条是竞态防线,不是可选优化。

## 所有权协议:谁该停内核

现有换代守卫维护的是"**组件**拥有内核"的模型(`lastBackendGen` 存在组件里,cleanup
条件停止)。本方案改成"**会话**拥有内核",必须显式重定义,不能只说"守卫全部保留"。

抽成纯函数便于测试:

```
shouldStopOnCleanup(lastBackendGen: number | null, sessionGen: number | null): boolean
```

- 从未成功装载(`lastBackendGen === null`)→ 不停(无核可收)
- 本组件装的核**正是活动会话**(两者相等)→ **不停**(会话接管所有权)
- 其余(会话为空,或会话已换到别的代次)→ 停,语义同现状

在途装载返回后 `gen !== loadGen` 的条件停止**保持不变**——那条防的是"迟到装载掐掉
新页面",与所有权无关。

## 位置续播

右键浮层「回到笔记」回笔记页 → `AudioPlayer` 重新 `player_load` → 新核从 0 起。要续上必须
显式 seek:

- 笔记页在装载完成回调(`onLoaded`)里,若**当前会话的 noteId 等于本页笔记**,
  则 `player_seek(session.currentMs)`,并在会话原本 `playing` 时 `player_play`。
- 复用现有的 `pendingResume` 通路(A/B 切换保位置用的就是它),不新造机制。

## 各条退出路径

| 路径 | 处理 |
| --- | --- |
| 开始录制 | `recording.start()` 前置:有会话则 `player_stop` + 清会话 |
| 删除笔记 | 侧栏删除确认后、调删除命令前:若会话是这篇则 `player_stop` + 清会话。**必须覆盖"从侧栏删除非当前页笔记"**——mmap 让已删文件在 Unix 上继续可播,Windows 上活动映射还可能让删除失败 |
| 笔记改名 | store 订阅既有 `note_renamed` 事件刷新 title,否则后台播放期间改名会让浮层的悬停提示标题过期 |
| 关主窗口(托盘常驻) | 窗口只是隐藏、进程还在,音频**继续播**。这是刻意的(与音乐 App 一致)。托盘菜单的「停止播放」项**已补齐**(2026-08-15,见下节),不必再重开窗口 |
| 真正退出 | `PlayerHandle` drop → sender 断开 → 流线程退出 → 映射随进程回收,无需额外处理 |

## 测试

初版的测试计划避开了风险最高的部分(改了 cleanup、在途装载、跨路由所有权,却说
"不改那部分语义")。修正后:

**纯函数单测**(vitest,与 `audioScheme.ts` 同款):
- `shouldStopOnCleanup` 三分支:无核 / 会话持有 / 会话为空或已换代
- `shouldShowMiniPlayer`:有会话且在其他页 → true;在本笔记页 → false;无会话 → false;
  路由带查询串、尾斜杠等变体不误判
- 会话状态机:建立 / 各条结束路径 / 播放自然结束保留会话
- 事件代次过滤:`gen` 不匹配的位置事件必须丢弃(这是 P1 竞态的直接回归)

**并发路径靠真机冒烟**(前端无组件测试基建,不为此新建):
- 成功装载后卸载 / 装载中卸载 / A→B 快速连点 / 回 A 续播 / 从未播放就离页 / 删除活动笔记

## 托盘「停止播放」(2026-08-15 补齐)

关掉主窗口后音频继续响,而浮层随窗口一起看不见了——那一刻托盘是唯一能停它的地方。

**出现条件 = 有播放会话**,与浮层同源(会话由"真正开始播放"建立,装载不算),
但**少一条 pathname 判定**:浮层在笔记本页上要给完整播放器让位,托盘不需要——
窗口都关了,谈不上"页面里有播放器"。会话语义在前端,后端只有装载代次,故由前端
经 `set_playback_active` 告知(`AppState.playback_active`),值真变了才重建菜单——
前端 effect 会因会话对象换引用(改名/重装)重发同一个值。

**为什么不让后端自己判**:后端能看到的只有"有没有装载内核",而进笔记页就自动装载,
拿它当条件会让只看过、没播过的笔记也在托盘冒出「停止播放」。

**为什么要广播 `player_stopped`**:命令式的 `player_stop` 是前端自己发起的,它知道自己
停了;托盘这一路是**后端发起**的,不广播就会留下一个指着已死内核的会话——浮层挂着旧
笔记、进度僵住、按钮点不动(正是 `player_stop` 注释里那条悬空会话失败模式)。事件带
被停掉的那一代 `gen`,收方只清自己名下的:

- `playback.stopped(gen)`:代次相符才清会话(不符 = 这条属于旧内核,当前会话是它之后
  新起的,清了就误杀正在播的那篇)。
- `AudioPlayer`:代次相符则复位按钮/进度、清 `lastBackendGen`,并自增 `reloadKey` 重装
  一次——核已经被拆了,不重装的话再点播放会打到空内核报「尚未装载音轨」。重装后回到
  "进页面刚装好、停在 0"的状态。

**不碰窗口**:从托盘停播的人本意就是不想让窗口跳出来,故不 `show()`/`set_focus()`。

冒烟:
- [ ] 播放中打开托盘菜单 → 有「停止播放」;没在播时**没有**这一项
- [ ] 关掉主窗口(托盘常驻)→ 音频继续 → 托盘「停止播放」→ 音频立刻停
- [ ] 停完重开窗口 → 浮层已消失,回到那篇笔记页,播放器停在 0 且**能再播**
- [ ] 就停在笔记页上从托盘停播 → 页内播放器按钮回到"播放"态、进度归 0、能再播
- [ ] 切英文界面 → 该项文案为 "Stop playback"
