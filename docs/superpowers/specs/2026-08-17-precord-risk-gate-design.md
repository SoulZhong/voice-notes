# 开录前风险拦截设计

## 由来

2026-08-17 一场 22 分 54 秒的在线会议(笔记 `20260817-112430`,蓝牙耳机 + 语音突显)损失了两大块内容:

| 损失 | 占比 | 成因 | 当时的应对 |
|---|---|---|---|
| 硬件断流补零 | 14.2%(194.6s) | 蓝牙 HFP 麦克风 | 无任何提示 |
| 系统削零 | ~27% | macOS 语音突显 | **横幅在显示,用户照录了** |

关键事实是第二行:应用早就有语音突显的告警横幅(`micModeBad`,4 秒轮询),那场也确实触发了(日志 `[采集] 麦克风模式=语音突显` 与 `普通麦克风已启动: 16000 Hz` 相邻),但内容还是丢了。**被动横幅这个形式已被实证无效。**

而这两个条件都是开录前就能知道的。

## 目标

把「开录前可知、且会实质损坏录音」的条件,从被动横幅升格为一次开录前确认。

非目标:成为门禁。用户明知有损失也要马上开录(会议已经开始了)是合理场景,必须留出口。

## 推翻的既有决定

`mic_mode` 命令的文档写着「只报状态不拦录制——它是提示,不是门禁」。本设计推翻其中一半:改为拦一次、可继续。保留的一半是「用户始终能录」。

## 触发条件

只收本次有实测证据的两条,不做通用风险框架:

| kind | 判据 | 后果 |
|---|---|---|
| `voice_isolation` | `mic_mode::active().damages_audio()` | 系统把非人声削成绝对零,判错时连人声一起削 |
| `bluetooth_mic` | 默认输入设备传输类型为蓝牙 | HFP 上行与会议软件争带宽,间歇断流 |

输入音量过低、蓝牙输出回声风险这两条既有横幅**不并入**:前者用户可一键修复且不损坏内容,后者影响的是回声消除效果而非内容完整性,量级不同。

## 架构

### 后端:一个命令给出真值

```rust
#[tauri::command]
fn precheck_recording() -> Vec<RecordRisk>   // { kind: String, detail: String }
```

组合逻辑放后端而不是前端调两次:拦截点要的是「有没有风险」这**一个**判断,将来别的入口(托盘、快捷键补提示)读同一份真值,不各自拼装。

新增 `audio::default_input_is_bluetooth()`,照 `default_output_is_bluetooth()` 写,selector 换成 `kAudioHardwarePropertyDefaultInputDevice`。查询失败一律按「非蓝牙」处理,不挡任何流程——与既有惯例一致。

### 前端:两个按钮入口共用一个守卫

录制页与侧边栏都走同一个 `startRecordingGuarded()`,不各写一遍。

流程:调 `precheck_recording()` → 有风险则弹确认(逐条列出后果与改法)→ 两个出口「去改设置」(不开录)/「仍然录制」(开录)。

### 抑制策略

选「仍然录制」后,**该 kind 在本次应用会话内不再拦**(内存变量,不落盘)。

理由:固定用蓝牙麦的人每次开录都被拦,会训练出闭眼点击,那就退化成这次失效的横幅了。不落盘则保证重启后重新提醒,不给永久静音的出口。

### 开录入口全表(Codex review 补全)

初稿只数了两个按钮入口,漏了两条:

| 入口 | 有 UI 上下文 | 处理 |
|---|---|---|
| 录制页按钮 | 是 | 拦 |
| 侧边栏按钮 | 是 | 拦 |
| **笔记详情页续录** | **是** | **拦**(初稿漏了;续录重新打开同一套采集链,风险完全相同) |
| 全局快捷键 / 托盘 | 否 | 不拦,见下 |
| **MCP `start_recording`** | **否** | **不拦,但把风险随返回值带给调用方**(见下) |

### 快捷键/托盘路径

不拦,照录。

`shortcuts.rs` → `crate::toggle_recording(app)` 是纯后端路径,没有 UI 上下文;为确认而唤起窗口抢焦点,会毁掉快捷键「不打断、立刻开录」的价值。

**已知限制**:仓库没有通知插件,所以这条路径的事后提示只能落在录制页横幅上——用快捷键开录且不在录制页的用户看不到。要跨页面提示需引入 `tauri-plugin-notification`(新依赖 + macOS 通知授权),本版不做。作为补偿,把 `bluetooth_mic` 加进现有横幅体系(`micModeBad` 已在其中),使录制页至少两条风险都可见。

### MCP 路径

同样无 UI 上下文,拦不了;但它比快捷键更糟——**不会把用户导航到录制页**,横幅兜底也不成立。
处理:`start` 的返回值带上 `risks` 数组,让 AI 助手能把风险转达给人,而不是静默录一场残缺的会。

## 测试

- 后端:`RecordRisk` 组装(两条风险的有/无组合);`default_input_is_bluetooth` 查询失败回落 false 不 panic。
- 前端:precheck 空 → 直接开录;非空 → 不开录且弹窗;选「仍然录制」→ 开录,且同 kind 第二次不再拦。

## 二轮审查后的补充(断流风暴提示)

风暴提示原先把状态放在录制页组件里,有两个真问题(Codex 二轮 P2):

1. 录制中离开 `/record` 再回来,页面重新挂载、局部状态归零;而后端此时 `armed=false`,持续中的风暴不会重发上升沿,横幅在风暴仍在继续时永久消失。
2. 停录后仍在途的事件能把横幅重新点亮,而那之后 tap 已结束,永远不会再有平息沿。

改为模块级 store `gapStorm.svelte.ts`,订阅在 layout 起(与 `startPlaybackSubscriptions` 同一条教训:放组件里,组件一卸载订阅就没了),非录制期事件一律不收。纯转移函数拆在 `gapStorm.ts` 便于测试。

**已知覆盖限制**:风暴判据是 `hw_gap_ms`,只在硬件时戳判洞分支增长,所以拿不到时戳的后端(Windows loopback)永远报不出风暴。这是刻意保留的——那个平台「无播放即无回调」,补零本就是常态,拿补零量当判据会把静音全报成风暴,等于用一个漏报换满屏误报。macOS 双轨与 Windows 的 mic 轨都不受此限。
